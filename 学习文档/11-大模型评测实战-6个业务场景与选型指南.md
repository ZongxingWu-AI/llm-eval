# 大模型评测实战：6 个业务场景与选型指南

---

掌握 LLM-as-Judge 等评测工具，解决的是**"怎么评"**的问题。但在实际业务中，**"为什么评"和"评什么"**往往比"怎么评"更前置、更关键。不同业务阶段对应不同的评测目标、方法、工具与验收标准，场景判断失误，工具投入将难以产生实际价值。

## 🎯 一、为什么业务场景是评测的第一性原理

### 1 从工具到场景：评测思维的转变

当前业界关于大模型评测的讨论，大量集中在工具层面——如何用 LLM-as-Judge 打分、如何搭建 CI/CD 评测流水线、如何用 promptfoo 做红队测试。这些工具解决的是**"怎么评"**的技术问题。

但在真实业务中，**"为什么评"和"评什么"才是决定评测有效性的前提**。同一套评测工具，在技术选型场景下用于横向对比，在模型迭代场景下用于纵向基线，在安全合规场景下用于主动攻防——目标不同，方法完全不同。

### 2 场景化思维对工作方法的价值

在实际工作中，评测需求通常由不同角色提出，对应不同的决策链条：

- **CTO / 架构师**：关注"该选哪个模型"，需要横向能力对比与性价比评估
- **算法工程师**：关注"新版本有没有退步"，需要纵向基线与维度级拆解
- **安全团队**：关注"能不能被越狱"，需要主动攻击与合规映射
- **产品经理**：关注"RAG 系统答得准不准"，需要检索质量与生成忠实度

如果缺乏场景意识，评测活动容易陷入**"为了跑分而跑分"**的困境——跑完公开榜单，发现与业务需求脱节；跑完安全扫描，发现未覆盖业务特有攻击面。场景化思维的核心价值在于：**将评测目标与业务决策对齐，避免资源浪费与方向偏差**。

### 3 场景化思维对求职面试的价值

在大模型相关岗位的面试中，"评测"是高频考察点。面试官通常关注的不仅是候选人对工具的了解程度，更是**对业务场景的理解深度**。

**💡 面试场景示例**：面试官问"如何评测 RAG 系统"，期望听到的不是工具列表，而是**"检索与生成需解耦评估"**的场景化思路。面试官问"如何验证新版本模型"，期望听到的不是"跑一遍测试集"，而是**"建立基线 → 维度拆解 → 线上 A/B 验证"**的完整闭环。面试官问"模型安全性如何保障"，期望听到的不是"做了过滤"，而是**"红队对抗 + 合规映射 + 持续监控"**的体系化方案。

**能够将评测工具与业务场景精准对应，是区分"工具使用者"与"业务驱动者"的关键标志。**

## 🏗️ 三、场景详解（上）：技术选型 / 模型迭代 / 安全合规

### 1 场景 1：公司级技术选型

**触发背景**：企业计划接入大模型能力，需在多个候选模型中确定最终接入方案。此时面临的核心问题是：公开榜单排名不一致，且榜单分数与业务实际表现存在偏差。

**核心诉求**：

- **横向对比**：同一测试集上运行多个模型，量化能力差异
- **覆盖全面**：评测维度需覆盖学科知识、逻辑推理、代码生成、中文理解等基础能力
- **结果可信**：优先采用第三方公开榜单，避免仅参考厂商自评分数
- **决策导向**：输出可指导采购决策的量化报告

**执行路径**：

**第一步：公开榜单基准测试**

- **C-Eval**：覆盖 52 个学科，共 13,460 道题目，侧重中文知识推理
- **MMLU**：覆盖 57 个学科，侧重英文多任务语言理解
- **CMMLU**：MMLU 的中文扩展版本
- **司南竞技场**（opencompass.org.cn/arena）：支持在线模型 PK，无需本地部署

**第二步：业务测试集验证**

从真实业务中抽取 50–100 条样本构建私有测试集。榜单评测的是通用能力，业务测试集验证的是"能否解决实际问题"。

**⚠️ 实践观察**：部分客服类业务中，榜单排名靠前的模型在中文口语理解（如"嗯""哦""意思意思"等模糊表达）上表现弱于排名靠后的模型。

**第三步：性价比评估**

在能力差距小于阈值（如 3%）的前提下，需综合评估 API 单价与日均调用量。以日均 100 万 Token 为例，单价 0.001 元/千 Token 与 0.01 元/千 Token 的年成本差异约为 **3,285 元 vs 32,850 元**。

**常见风险**：

- **风险一**：仅依赖榜单分数，未运行业务测试集
- **风险二**：使用 LLM-as-Judge 进行单轮打分，未做 Position-Swap 校验（交换 A/B 答案位置后，评分结果可能反转）

**核心要点**：技术选型的本质是"横向 PK + 业务题验证"。公开榜单提供基线参考，业务测试集提供决策依据。

### 2 场景 2：基模厂商的模型迭代

**触发背景**：基模团队完成新版本训练后，需验证 V2 版本相对 V1 版本是否存在能力退化或特定维度下滑。

**核心诉求**：

- **纵向对比**：新版本 vs 旧版本的细粒度差异
- **维度拆解**：不仅关注总分，需拆解至学科级、能力级（数学 / 代码 / 写作等）
- **自动化**：评测流程需集成至 CI/CD，支持每次发版自动触发
- **可复现**：固定随机种子，设置 Temperature = 0，确保相同输入多次运行结果一致

**执行路径**：

**第一步：建立基线**

V1 版本运行全量评测（如 C-Eval 全量 + 业务测试集），记录各学科准确率作为基准值。

**第二步：版本对比**

V2 版本运行同一套测试集，生成差异报告：

| 学科/能力 | V1 准确率 | V2 准确率 | 变化 |
|---|---|---|---|
| 数学 | 31.6% | 35.2% | +3.6% |
| 逻辑推理 | 72.0% | 68.5% | -3.5% |
| 中文写作 | 85.0% | 87.0% | +2.0% |
| **总分** | **74.1%** | **76.3%** | **+2.2%** |

**⚠️ 关键提示**：总分上涨不代表各维度均上涨。上例中逻辑推理下降 3.5%，若业务强依赖推理能力，该退化可能比总分上涨更具风险。

**第三步：线上 A/B 验证**

基线测试通过后，灰度 5% 流量至新版本，监测用户反馈指标（点赞率、停留时长、投诉率）。

**常见风险**：

- **风险一**：仅关注总分变化，未进行维度级拆解
- **风险二**：未固定随机种子或 Temperature 参数，导致基线对比失去统计意义

**核心要点**：模型迭代的本质是"纵向基线对比 + CI/CD 自动化"。总分是结果，维度拆解才是风险预警。

### 3 场景 3：面向安全与合规的攻防测试

**触发背景**：模型上线前，合规部门要求提供安全性证明，验证模型是否存在越狱、提示注入、PII 泄露等风险。

**核心诉求**：

- **主动攻击**：模拟真实攻击手段，在上线前发现漏洞
- **覆盖全面**：覆盖越狱、注入、PII 泄露、偏见、有害内容等攻击向量
- **合规映射**：测试结果需映射至 OWASP LLM Top 10、NIST AI RMF、EU AI Act 等标准
- **可复现**：漏洞需可稳定复现，修复后需可验证

**执行路径**：

**第一步：红队扫描**

使用 promptfoo 启动自动化红队测试：`npx promptfoo@latest redteam run`

该命令可自动生成数百个攻击 Prompt，覆盖越狱、注入、PII 泄露等 10 余类攻击向量。

**第二步：安全报告分析**

典型报告结构如下：

| 攻击类型 | 攻击数 | 成功数 | 风险等级 |
|---|---|---|---|
| 越狱（Jailbreak） | 50 | 12 | 高 |
| Prompt 注入 | 30 | 5 | 中 |
| PII 泄露 | 20 | 0 | 低 |
| 有害内容 | 40 | 8 | 高 |

风险等级为"高"的项需在上线前完成修复。

**第三步：合规映射**

- **OWASP LLM Top 10**：对应 LLM01–LLM10 风险项
- **NIST AI RMF**：对应 Govern / Map / Measure / Manage 四阶段
- **EU AI Act**：对应 Article 5 / 14 / 15 风险条款

**常见风险**：

- **风险一**：将红队测试视为一次性活动，未建立持续监控机制
- **风险二**：仅测试通用攻击，未覆盖业务特有攻击面（如金融模型被诱导输出投资建议、医疗模型被诱导开具处方）

**核心要点**：安全合规的本质是"主动攻击 + 合规映射"。红队测试不是一次性检查，而是持续对抗过程。

## 🔍 四、场景详解（下）：RAG / Agent / 多模态与长文本

### 4 场景 4：RAG 与知识库系统评测

**触发背景**：企业基于大模型构建知识库问答系统（RAG）时，需验证"检索到的内容是否相关"以及"生成的答案是否忠实于检索结果"。

**核心诉求**：

- **检索质量**：验证召回文档的相关性与覆盖率
- **生成忠实度**：验证生成内容是否基于检索文档，而非模型幻觉
- **答案相关性**：验证最终回答是否准确回应用户问题
- **抗噪声能力**：验证系统在部分检索结果错误时的表现

**关键指标**：

| 指标 | 定义 | 常用工具 |
|---|---|---|
| **Context Precision** | 检索结果中相关文档的比例 | RAGAS |
| **Context Recall** | 真实所需文档被成功召回的比例 | RAGAS |
| **Faithfulness** | 生成答案与检索文档的事实一致性 | RAGAS / TruLens |
| **Answer Relevance** | 答案与问题的语义匹配度 | Ares / DeepEval |

**执行路径**：

1. 构建包含标准答案的 RAG 测试集（Query + 期望检索文档 + 期望答案）
2. 运行端到端评测，分别计算检索指标与生成指标
3. 对检索失败案例进行 Bad Case 分析，优化 Embedding 模型或分块策略

**核心要点**：RAG 评测需将"检索"与"生成"解耦评估。检索失败导致的答案错误，应优先优化向量数据库或分块策略，而非替换生成模型。

### 5 场景 5：Agent 与工具调用评测

**触发背景**：大模型 Agent 需自主规划任务、选择工具（Function Calling）并执行多轮交互。评测重点从"单轮回答质量"转向"多轮任务完成度"。

**核心诉求**：

- **任务完成率**：Agent 是否成功达成预设目标
- **工具选择准确率**：模型是否调用了正确的 API / 工具
- **规划合理性**：多步任务中的步骤是否高效、无冗余
- **错误恢复能力**：工具调用失败后，Agent 是否能调整策略

**关键指标与工具**：

| 评测维度 | 代表基准 | 核心指标 |
|---|---|---|
| 通用 Agent 能力 | AgentBench | 任务成功率、平均步骤数 |
| 工具调用 | ToolBench | 工具选择准确率、参数填充准确率 |
| 代码生成与修复 | SWE-bench | 补丁应用成功率 |

**执行路径**：

1. **定义任务边界**：明确 Agent 的可用工具集与任务目标
2. **构建测试用例**：覆盖单工具调用、多工具串联、工具调用失败等场景
3. **运行自动化评测**：记录任务是否完成、步骤数、工具调用序列是否正确

**核心要点**：Agent 评测的核心是"端到端任务成功率"。中间步骤的工具调用准确率是过程指标，最终业务目标的达成率才是验收标准。

### 6 场景 6：多模态与长上下文评测

**触发背景**：随着 GPT-4V、Gemini、Qwen-VL 等多模态模型及 128K/1M 长上下文模型的普及，评测需求从纯文本扩展至图文理解与长文本处理。

**核心诉求**：

- **多模态理解**：验证模型对图像、图表、文档截图的信息提取与推理能力
- **跨模态一致性**：验证图文混合输入下的逻辑一致性
- **长文本检索**：验证模型在超长文本中定位关键信息的能力（"大海捞针"）
- **长程依赖**：验证模型对长文档前后文关联的理解能力

**关键指标与工具**：

| 评测维度 | 代表基准 | 测试重点 |
|---|---|---|
| 多模态推理 | MMMU / MMBench | 大学级别多学科图文理解与推理 |
| 图表理解 | ChartQA / MathVista | 图表、数学公式识别与计算 |
| 长文本检索 | LongBench / RULER | 不同长度文本中的关键信息定位 |
| 长程依赖 | L-Eval / InfiniteBench | 超长文档的摘要、推理与一致性 |

**执行路径**：

1. **多模态评测**：选取覆盖图表、文档、自然图像的测试集，验证模型在 OCR、视觉问答、跨模态推理上的准确率
2. **长文本评测**：采用"大海捞针"（Needle in a Haystack）方法，在超长文本中插入特定信息，测试模型能否准确提取
3. **性能衰减分析**：记录模型在不同上下文长度（4K / 32K / 128K）下的指标衰减曲线

**核心要点**：多模态评测关注"跨模态信息对齐"，长文本评测关注"信息不随长度增加而丢失"。两者均需使用专门设计的基准测试集，通用文本评测无法覆盖。

## ✅ 六、结语

大模型评测的价值不在于分数本身，而在于**评测目标与业务阶段的对齐**。

| 场景 | 核心逻辑 | 验收标准 |
|---|---|---|
| 技术选型 | 横向对比 + 业务验证 | 选对模型，控制成本 |
| 模型迭代 | 纵向基线 + 自动化 | 能力不退步，风险可预警 |
| 安全合规 | 主动攻击 + 合规映射 | 上线前消除高危漏洞 |
| RAG 评测 | 检索与生成解耦评估 | 答案忠实、检索精准 |
| Agent 评测 | 端到端任务驱动 | 任务完成率达标 |
| 多模态/长文本 | 跨模态与长程能力验证 | 信息不丢失、模态可对齐 |

明确所处场景后，再选择工具与制定评测方案，可避免资源浪费与方向偏差。
