# 法律领域 Benchmark 项目：岗位共性与简历表述

> 用途：将本项目包装为“大模型评测工程闭环”项目，适用于大模型评测工程师、LLM 数据/质量、Benchmark 研究、评测平台和部分 Agent 数据评测岗位。
>
> 当前版本基于 `学习文档/岗位jd.md` 中整理的 21 份岗位 JD，以及截至 **2026 年 8 月 28 日**仓库内实际存在的代码、数据产物和运行元数据。
>
> 使用原则：简历只写能够由代码、数据文件、metadata、manifest 或运行报告证明的事实；未完成正式运行的结果统一使用条件化表述或占位符。

## 一、岗位共性：企业真正想招什么人

这批 JD 的共同画像不是“会调用大模型的人”，而是：

> **能把模型问题拆成评测目标，设计数据与评分标准，搭建自动化评测链路，分析模型缺陷，并推动后续迭代的 LLM Evaluation / Benchmark 工程师。**

### 1. 评测闭环能力是主线

多数岗位期待的完整链路是：

```text
业务/模型问题
→ 能力目标拆解
→ 评测任务与数据集
→ Rubric / Grader / Verifier
→ 批量模型评测
→ 结果统计与 Bad Case 分析
→ 数据或模型迭代
```

因此，简历不能只写“做了数据清洗”“跑了模型”“做了标注”“调了 Prompt”，而要写成：

> **围绕某类模型能力，完成任务设计、数据构建、自动评分、质量验证和结果分析。**

### 2. Benchmark 与评测任务设计

高频要求包括：

- 把抽象的模型能力拆成可测试任务；
- 定义能力边界和评测维度；
- 建设通用或垂直领域 Benchmark；
- 设计不同难度、风险等级和任务类型的样本；
- 跟进并接入公开评测集或前沿评测方法。

对应关键词：

- Benchmark；
- Evaluation Dataset；
- Task Design；
- Capability Taxonomy；
- Test Case；
- Data Standard；
- Evaluation Criteria。

### 3. 评分器和评测方法可靠性

这是普通数据岗位和专业评测岗位的关键区别。JD 普遍关注：

- 主观题自动评测；
- LLM-as-a-Judge；
- Rubric、Grader、Verifier；
- 人工复核和 Calibration；
- 评分一致性与可解释性；
- 判分偏差、抗刷分和评分漏洞；
- 数据泄漏与题目污染。

简历要体现的不是“让模型打分”，而是：

> **设计了与任务类型匹配的评分方法，并考虑结果是否可解释、可复核和可定位。**

### 4. 数据质量、版本和可追溯性

高频要求包括：

- 数据收集、清洗、合成和抽样；
- 样本规范、标注规范和质检规则；
- 交叉复核、质量验收和数据迭代；
- 数据版本、来源追踪和结果复现；
- 将数据标准落实为可执行的校验流程。

企业看重的不是单次产出一批数据，而是能否沉淀为稳定的数据生产和质量控制体系。

### 5. Python 自动化和工程化

评测岗位普遍要求：

- Python；
- 批量模型调用；
- 自动化评测脚本或框架；
- CLI、日志、错误记录和运行 metadata；
- 并发、限流、稳定性和执行效率；
- 统计分析、报告生成和结果可视化。

部分岗位还要求 SQL、Excel、PyTorch、OpenAI-Compatible API、Prompt Engineering、Agent / Workflow / Function Calling。Python、数据处理和自动化评测是基础能力；Agent、多模态、SFT/RL、PyTorch 更像是不同岗位的加分项。

### 6. Bad Case 分析和模型迭代

岗位不满足于“跑出一个分数”，而是希望回答：

- 模型错在哪里；
- 是模型、数据、题目、评分器还是环境问题；
- 错误集中在哪些任务和场景；
- 是否存在数据泄漏或判分漏洞；
- 下一步应补什么数据、改什么 Prompt 或调整什么模型。

因此，简历应从“数据生产”升级到：

> **基于评测结果定位模型能力缺口，并为模型迭代提供可执行依据。**

但当前项目尚未落盘正式模型评测结果，暂时不能写成已经完成模型 Bad Case 分析或效果提升。

### 7. 研究意识和问题定义能力

研究型岗位还关注：

- 是否能从第一性原理定义评测问题；
- 是否理解模型能力边界；
- 是否能提出新的评测标准；
- 是否理解预训练、后训练、数据和评测之间的关系；
- 是否阅读论文和跟踪前沿 Benchmark；
- 是否有可复现的个人研究产出。

当前项目可以体现问题定义、评测方法论和工程研究意识，但没有论文、模型训练或效果对比实验时，不应包装成训练研究项目。

### 8. 协作和项目推进能力

不少岗位要求与产品、算法、工程、标注和训练团队协作。如果没有真实协作证据，不建议在简历中写“协同多团队推动落地”。当前项目更适合使用：

> **个人项目｜独立设计与实现**

突出独立完成问题定义、代码实现、数据链路和质量控制设计。

## 三、当前项目的事实边界

### 暂时不能直接写进简历

除非仓库外已有对应运行产物，否则不要写：

- 已完成正式题集发布；
- 已完成 X 道题的完整模型评测；
- 模型准确率达到 X%；
- 评分器与人工评分一致率为 X%；
- 模型效果提升 X%；
- 已完成完整 Bad Case 分析；
- 已构建 Agent、Function Calling 或多模态评测集；
- 参与 SFT、RLHF、RLAIF 或模型训练。

### 数据口径注意事项

1. `raw` 中是 50 份案件文件，`README.md` 不是案件，不能把目录文件总数写成 51 个案件。
2. 当前 clean/extract 的实际分类数量为：

```text
合同、准合同纠纷：11
婚姻家庭、继承纠纷：11
劳动争议：19
侵权责任纠纷：4
物权纠纷：5
```

可以写“覆盖 5 类民事纠纷，共 50 个案件”，但不能写“5 类纠纷各 10 个案件”。
3. 当前 clean 数据中仍有部分记录处于 `needs_review` 状态，extract 记录的质量状态也仍建议复核。因此应写“建立了数据质量校验和来源追踪机制”，不要写“完成了全部数据的人工高质量审核”。
4. 当前 `drafts`、`releases` 和 `results` 目录主要是说明文档，正式题集发布、完整模型评测和人工 Calibration 结果尚未形成可引用产物。

## 四、三类目标岗位的简历版本

### 版本 A：评测工程 / Benchmark 岗位

**项目名称：** 法律垂直领域大模型评测 Benchmark 与自动化评测流水线

**项目性质：** 个人项目｜独立设计与实现

**技术栈：** Python、OpenAI-Compatible API、JSONL、JSON Schema、Taxonomy、LLM-as-a-Judge、Rubric、Excel

**项目描述：**

- 面向法律垂直领域大模型评测，独立设计并实现从真实民事判决书解析、法律信息抽取、候选题生成、题集校验到模型批量评测的流程化框架，形成 `raw → clean → extract → drafts → releases → validation → evaluation` 的标准数据链路。

- 基于 50 份真实民事一审判决书，覆盖合同、劳动、侵权、婚姻家庭/继承、物权等 5 类民事纠纷；围绕事实抽取、争议焦点识别、法律规则适用、证据评价、裁判结果和金额计算等能力设计结构化评测任务。

- 实现规则提取与 LLM-grounded 提取双路径：通过案件级 `case_id`、原文章节、`source_quote` 和 SHA-256 来源指纹建立数据追踪机制，并对模型生成的法律结论执行来源章节和原文证据回查，降低无依据内容进入下游流程的风险。

- 设计并实现题集构建、受控 Taxonomy、JSON Schema 校验、案件级 `dev / calibration / test` 划分和同案防泄漏机制，保证题目字段、分类标签、来源证据和数据划分具备可验证性和可复现性。

- 实现 `rule / redline / rubric_judge` 三类法律回答评分器，统一输出 `PASS / REVIEW / REJECT`，并记录评分理由、错误信息、响应延迟、Token 消耗和运行 metadata，为后续模型能力分析和评测报告生成提供结构化数据。

**主要命中关键词：** 评测框架、Benchmark、Python、数据处理、自动化评测、Rubric、Grader、可追溯、可复现、评测报告。

### 版本 B：Agent / 数据质量 / 评测岗位

> 当前项目没有 Agent 或 Function Calling 实现，因此这一版突出任务拆解、数据规范、质量体系和评分器能力，不把项目虚构为 Agent 项目。

**项目描述：**

- 将法律模型能力拆解为事实理解、争议识别、规则适用、证据评价、裁判结论和风险拒答等可验证任务，并为任务配置参考答案、必答点、扣分项、风险等级、评分方式和原文证据。

- 围绕真实判决书建立案件级数据生命周期，设计 `case_id`、来源文件、SHA-256、章节定位和处理 metadata 等追踪字段，使案件、抽取结果、候选题和后续评测结果能够回溯到原始文本。

- 通过受控 Taxonomy、JSON Schema、来源章节校验、原文短引回查、重复检查和案件级 split 规则建立数据质量控制流程，避免标签失控、证据失真和同案跨集合泄漏。

- 设计候选题默认 `pending`、人工审核后进入 release 的题集流程，并将结构化规则评分、红线检查和开放式 Rubric 裁判统一到同一评分接口，支持后续人工 Calibration 和自动评分可靠性验证。

- 通过模块化 CLI、JSONL 输入输出、错误文件、运行 metadata 和独立结果目录，提升数据处理和批量评测流程的可复现性、可定位性和交付规范性。

**适合强调：** 数据标准、质检规则、数据可追溯、任务规范、Rubric、Grader、数据交付、自动化流程。

**当前不要写：** Agent 长程任务评测、Function Calling 评测、工具调用轨迹分析、Agent Workflow 搭建。

### 版本 C：评测研究 / 模型能力分析岗位

**项目描述：**

- 针对法律问答不能仅依赖文本相似度评价的问题，构建覆盖事实准确性、争议焦点、法律规则适用、证据支持、裁判结论、金额计算和合规拒答的多维能力评测框架。

- 基于真实民事判决书设计垂直领域 Benchmark，将案件文本转化为带有参考答案、评价维度、必答点、扣分项和来源证据的任务化评测样本，明确模型在法律理解和推理任务中的能力边界。

- 设计规则评分、红线检查和 LLM-as-a-Judge 三类互补评分方法：对确定性任务使用结构化规则，对风险拒答使用红线规则，对开放式法律论证使用 Rubric 裁判，提升不同任务类型下的评分适配性和可解释性。

- 通过案件级数据切分、来源证据回查、受控分类体系、运行 metadata 和结果报告机制，控制同案泄漏、证据不可验证和实验不可复现等评测风险。

- 为后续开展模型横向对比、人工 Calibration、评分器一致性分析和法律场景 Bad Case 归因，建立统一的数据接口和实验记录基础。

**适合强调：** 问题定义、能力边界、评测方法论、评分可靠性、数据泄漏控制、可解释性和实验设计。

## 五、正式评测完成后的结果导向写法

完成候选题审核、release 发布、模型批量评测和人工 Calibration 后，可以把以下占位符替换成真实数据：

- 基于 50 个真实法律案件构建并发布 **X 道评测题**，覆盖 **X 类任务**和 **X 种模型能力**。
- 完成某模型 **X 次模型调用**，调用成功率 **X%**，并按案件类型、任务类型、数据 split 和评分方式拆解模型错误分布。
- 在 **X 道 Calibration 样本**上进行人工复核，自动评分与人工判断一致率达到 **X%**，定位并修正 **X 类 Rubric 边界问题**。
- 通过评测结果识别模型在事实抽取、规则适用、证据评价、金额计算和合规拒答等维度的能力缺口，为后续数据补充和模型迭代提供依据。
- 统计模型平均响应延迟 **X 秒**、平均 Token 消耗 **X**，并通过批量调用、并发控制和结果缓存优化评测执行效率。

只有在对应文件和运行目录真实存在后，才应把这些内容写入正式简历。

## 六、面试主线

### 1. 问题定义

法律回答不能只看文本相似度，还要判断事实是否正确、法律规则是否适用、证据依据是否充分、金额计算是否正确，以及是否触发高风险错误。因此项目采用“结构化案件 + 任务化题集 + 分层 Grader”的设计，而不是简单的问答相似度评测。

### 2. 数据设计

从真实判决书中保留案件全文、案件主体、裁判理由、判决主文和来源位置，构建 `raw → clean → extract` 的数据生命周期；后续题目中的参考答案和 Rubric 通过来源章节、原文证据进行追溯，避免生成脱离上下文的问答对。

### 3. 题集设计

将案件拆解为事实抽取、争议焦点识别、法律规则适用、证据评价、裁判结果预测、金额计算和合规拒答等能力任务，为每道题配置参考答案、必答点、扣分项、风险等级和来源证据，并在发布前执行字段、标签、证据和 split 校验。

### 4. 评分设计

- `rule`：适用于答案关键点比较确定的结构化或半结构化任务。
- `redline`：适用于合规拒答、风险提示和禁止性表达检查。
- `rubric_judge`：适用于开放式法律论证，由裁判模型依据参考答案和 Rubric 进行判断。

三类评分统一输出 `PASS / REVIEW / REJECT`，同时保留评分理由和命中的评分点，便于错误定位和人工复核。

### 5. 可靠性控制

通过案件级切分避免同案泄漏；通过受控 Taxonomy 和 JSON Schema 约束题目字段；通过来源证据、哈希 Manifest、运行 metadata 和错误文件保证结果可追溯、可复现、可定位。

### 6. 结果分析

正式评测完成后，不只报告整体通过率，还应按数据集 split、任务类型、案件类型、评分方式和错误类型分析模型短板，区分模型能力问题、题目质量问题、评分器问题和模型调用/解析问题。
